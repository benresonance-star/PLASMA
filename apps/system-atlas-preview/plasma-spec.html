Geometry Resolver API · v0.4.26

PLS-GR-01 makes exact geometry resolution staged, inspectable and atomic

One entrypoint: resolve(request) executes nine typed stages—classify → infer intent → choose strategy → bind semantic references → apply tolerance policy → evaluate → validate → heal → commit. Every stage returns a status, decision, diagnostics, evidence and input/output digests; any hard ambiguity or failure can stop the pipeline without mutating accepted world state.

Exactness boundary: geometry providers such as OpenCascade execute candidate strategies in isolation. Plasma owns intent, reference binding, tolerances, semantic validation, bounded healing and commit. Raw provider handles remain ephemeral; semantic topology correspondence is rebuilt after topology-changing evaluation/healing and must be unambiguous for hard downstream references before commit.

Commit gate: exactness, validation, tolerance/healing budgets, semantic postconditions, topology correspondence, hard invariants, evidence completeness and the pinned base revision must all pass. Stale results return REVISION_CONFLICT; approximate preview geometry is never silently promoted to exact world geometry.

Pathology guard architecture · v0.4.23

PLS-16 gives Plasma an immune system without turning convention into law

PLS-16 screens proposed Transforms, isolated candidate worlds, project history and organization evidence for corruption, hard-governance conflict, known anti-patterns, pathological complexity, low-value/high-disruption changes and implausible consequences. It is an evaluation layer over the existing seven-primitives kernel, not an eighth primitive or competing issue database.

Authority boundary: kernel corruption and explicitly governed hard conditions may block publication; domain anti-patterns normally warn, hold or propose alternatives; novelty remains expressible through evidence-backed exception. AI plausibility/nonsense detectors are advisory by default and cannot make unconventional design illegal merely because it is statistically unfamiliar.

The same contract applies to humans, agents, solvers, imports and machines. Low-cost checks may run at preflight; candidate, project and temporal detectors run only at the fidelity and latency budget required by PLS-10/PLS-15.

Kernel architecture update · v0.4.18

Seven primitives, one governed mutation path

The canonical Plasma Kernel is compressed to Entity, State, Relation, Transform, Invariant, Event and Evidence. Architectural objects, intent schemas, geometry, fields, drawings, agents and simulations are domain layers above this kernel rather than additional kernel primitives.

Canonical mutation rule: no human, agent, solver, import, UI gizmo or external engine may directly mutate accepted world state. Every material change enters a transaction as a typed Transform against an immutable base revision, expands to primitive operations, computes the affected dependency closure, executes in an isolated candidate world, evaluates intersecting Invariants, resolves conflicts, and either commits atomically to a new revision or leaves the accepted world unchanged. Event records what actually happened; Evidence records why a state, relation, invariant, evaluation or decision is believed.

The semantic kernel remains authoritative and inspectable. Graphs, sparse matrices, tensors, execution DAGs, meshes, B-Reps, USD and solver models are compiled/derived computational representations. This permits CPU/GPU/NVIDIA-class acceleration without making any representation engine or vendor the owner of Plasma meaning.

Interaction architecture update · v0.4.17

Minimum irrelevant interface, not minimum capability

PLS-14 formalizes a three-layer lens stack over one authoritative Plasma world: Representation controls what is shown, Interaction controls which typed actions are surfaced and how, and Evaluation controls which consequences, criteria, fields and solvers matter now. A semantic-relevance resolver composes the stack from task, selection, dependencies, scale, authority, device and currentness rather than relying on camera zoom or hidden toolbars alone.

Relationships can appear as optional spatial bonds with typed provenance; direct edits enter speculative preview worlds; PLS-10 dirty-frontier/currentness data drives an honest blast-radius preview before publication. Explicit hierarchy and a stable Neutral/Inspect mode remain available. AI- or user-generated UI/capability changes follow propose → test-first contract → sandbox → guided human validation → affected-world replay → exact-digest acceptance → versioned promotion/rollback; silent overnight UI mutation is forbidden.

Source insight was selectively adapted from the 12 Sep 2026 “Minimalist Next-Gen CAD UI Design” exploration. The spec explicitly rejects cloud-only geometry as a premise, abolition of inspectable hierarchy, test-passing as proof of domain truth, and the claim that self-extending software makes technical debt impossible.

Deferred DifferentialContract

PLS-21 · PLS-DIFF-01@0.1.0 · architecture accepted 2 October 2026 · implementation NOT_STARTED

Status and authority

DEFERRED · ACCEPTED · NOT_STARTED · DISABLED · NON_AUTHORITATIVE_DERIVED. The contract sits outside the Plasma kernel. It may expose local model behaviour around an identified authoritative state but cannot directly mutate authoritative state, satisfy final validation or make a design decision.

Invariant: differential computation may guide authority, but may never silently become authority.

JVP

Forward sensitivity

JVP(Δx)=JΔx: predict local output deltas for a named perturbation. Uses include incremental prediction, selective recomputation and interaction preview.

VJP

Reverse sensitivity

VJP(v)=vᵀJ: expose local input leverage for an objective or constraint pressure. It guides search but never approves an edit.

VALIDITY + TRUST

Local only

Every result is anchored to a linearisation state, validity region and trust model. Known discontinuities override trust.

EXACT FALLBACK

Mandatory

Outside validity/trust, across discontinuities, near governed thresholds, at topology changes, final commit or regulatory decisions, the declared exact/validated/reference fallback takes over.

Claim · Evidence · DecisionContract

Claim: JVP predictions normally map to inferred; local sensitivities may map to calculated only when model/state/version/validity scoped. Exact results may supersede or contradict without erasing provenance.

Evidence: retain relevant input, solver, calibration, validation, benchmark, regulatory, measurement and derivation references. Numerical precision does not raise evidence quality.

DecisionContract: may consume leverage, marginal effects, recovery directions and exact-solver prioritisation; it retains decision authority, confidence policy, escalation, required evidence/validation and commit conditions.

Parametric architectural wall contract

PLS-19 · PLS-WALL-01@0.1.0 · specified 30 September 2026 · implementation unproven

Scope and authority

V1: straight/polyline paths, constant-height layered walls, supported junction policies, rectangular hosted openings and room-boundary integration. Curved/freeform walls, tapered layers and general junction solving are later extensions. Parameters and relations remain editable after generation. The wall package uses existing kernel and geometry contracts; it adds no kernel primitive.

Adapted from our SketchUp/MUZWalls discussion. This contract specifies Plasma behaviour and makes no claim about the plugin's internal implementation. Detailed schemas and acceptance assertions are included in the embedded manifest and export.

WALL-01

Path-driven construction

An explicit path, coordinate frame and pinned wall-system definition generate a wall. V1 supports straight segments and connected polylines. Curved paths and variable-height profiles are deferred extensions. Sketch interpretations remain proposals until adopted; raw marks and interpretation provenance remain addressable.

WALL-02

Editable parameters and ownership

Persist path and base elevation, height, system/type revision, reference-line role, lateral offset, orientation and layer definitions with units. Layers have stable IDs, ordered material references, thickness, function and explicit vertical extents. Total thickness is derived from layers. A total-thickness edit must name a layer-allocation policy or propose one; competing active writers are rejected. Reference line supports overall faces/centre and a declared core face/centre. Define left/right relative to path direction and preserve physical face intent when reversing the path.

WALL-03

Persistent junctions

Endpoint and crossing connections are semantic Relations with explicit policy: butt, miter or priority, layer participation and allowed tolerance. Resolve layers according to the pinned wall-system rules, not one universal wall algorithm. Moving or regenerating a wall reevaluates the relation. Unsupported joins remain unresolved; never silently fuse, change construction or accept a gap. Geometric coincidence alone does not create a persistent connection.

WALL-04

Hosted openings

Doors and windows retain stable identity, host relation, opening profile, width/height/sill and placement intent. Placement may be centred, fixed to a named jamb/endpoint, or a declared proportional rule. A driven placement has one active writer. Direct manipulation proposes a placement-rule change when needed. Wall movement or construction changes regenerate the opening; splitting/deleting the host requires explicit reassignment, detachment or rejection rather than nearest-object guessing.

WALL-05

Room and boundary relationships

Walls connect to room/space boundaries through explicit relations. Distinguish architectural reference dimensions from finished clear dimensions and declare which layer/face controls each measurement. Preview propagation strategies such as take space, preserve neighbour width or grow outward; name affected entities before acceptance. Wall geometry does not independently own room topology.

WALL-06

Non-destructive operations

CreateWall, SetWallParameters, MoveWall, StretchWall, SplitWall, JoinWalls, ChangeWallSystem and HostOpening are typed domain operations, not new kernel primitives. Define reads, writes, pinned base revision, references, units, scope, preconditions and impact. Use the PLS-17 operation/resolver boundary and PLS-GR-01 geometry verbs where needed; accepted feature state and relations determine evaluated geometry, not mesh indices or provider handles.

WALL-07

Bounded regeneration and correspondence

Invalidate only the affected dependency closure: connected junctions, hosted elements, room measures, exact/display geometry, analyses, quantities, cost and drawings. Preserve entity/layer/opening identity through regeneration, with explicit correspondence for topology changes. Stale-base results cannot overwrite newer state. Report ambiguity, pending, stale and failed outputs without discarding accepted facts.

WALL-08

Preview and exact acceptance

Provide immediate provisional feedback using the existing Interaction Reflex Runtime and Interactive Presentation Surface. Exact boundary representation geometry is resolved through the assigned geometry provider, initially OpenCascade, with declared tolerance, validation and evidence. Preview triangles cannot masquerade as exact geometry. Unresolved domain compliance may be explored under branch policy; hard integrity failures block commit and required issue/fabrication gates remain closed.

WALL-09

Derived quantities, cost and drawings

Generate revision-pinned plan/section/elevation views and quantities from the accepted feature state. Declare gross/net area and volume conventions, opening deductions, junction overlap allocation, layer scope and units to prevent double counting. Cost uses versioned rates with location/date, assumptions and uncertainty. Publication requires a mutually coherent set of results; each result records inputs, producer/version, parameters, fidelity, tolerance and currentness. A valid parametric wall alone proves no fire, acoustic, thermal, structural or regulatory performance.

WALL-10

Reusable and versioned wall systems

Store reusable construction, material and junction rules in the versioned Knowledge Ledger; projects pin exact system/rule versions. A library update triggers impact analysis and an optional evaluated migration branch, never silent regeneration of accepted projects. System definitions include applicability and fabrication/assembly constraints where known. Domain packs remain optional consumers of existing core contracts.

WALL-11

History, branching and tool round trips

Parameter changes, relation changes and accepted geometry retain Transform/Event/Evidence lineage. Undo appends a new revision; branches remain independently editable. Save/reopen preserves parameters, constraints, hosted identity and provenance. Imported/exported representations reconcile through explicit correspondence; an external wall mesh does not automatically become an editable parameter model.

WALL-12

Usable editing surface

Drawing a path, choosing a wall system and editing numeric parameters must remain available without AI services. Selection exposes concise wall parameters, reference line, hosts and junction policies; deeper inspection explains what drives each property and what an edit affects. Sketch, direct manipulation and language proposals converge on the same typed operations.

Required acceptance gates

All gates are required and unrun for this new contract. Historical wall-drag evidence alone does not satisfy them.

  1. WALL-AT-01 · Create and edit. Create a two-layer straight wall, then a polyline. Change height, base elevation, a named layer thickness and offset. Verify generated dimensions and reference-line placement within the declared tolerance; total thickness remains derived and physical face intent survives path reversal.
  2. WALL-AT-02 · Junction policies. Exercise L, T and crossing joins under supported butt/miter/priority policies with different layer configurations. Move an endpoint and regenerate repeatedly. Verify relation identity, declared layer termination and explicit unresolved status for unsupported/micro-gap/ambiguous cases.
  3. WALL-AT-03 · Hosted placement. Use both centred and fixed-jamb windows, resize and move the host, then change its construction. Verify opening/host identity and placement intent. Split/delete the host and require explicit disposition. Reject conflicting active placement writers.
  4. WALL-AT-04 · Rooms and conflicts. Move the bedroom/corridor boundary under take-space and preserve-neighbour strategies. Show the requested conflicted preview and affected rooms without silently changing strategy. Test the live fixture separately from synthetic data; do not substitute historic +315 mm synthetic values for the documented +150 mm live hard limit.
  5. WALL-AT-05 · Atomicity and stale work. Reject a stale-base wall edit; fail an exact geometry/junction operation; ensure accepted head and unaffected entities remain intact. Late geometry/quantity results cannot replace current outputs or enable publication.
  6. WALL-AT-06 · Quantity and document coherence. Compare layer volumes and opening deductions against independently calculated fixture expectations, including junction allocation. Update plan/section and cost after a parameter edit; all issued outputs refer to an explicitly coherent revision set.
  7. WALL-AT-07 · Branch, undo and reopen. Edit two branches independently, adopt one, undo, close and reopen in a normal storage origin. Recover from interrupted/corrupt persistence using the existing governed recovery path. Reconstruct system pins, parameters, relations, outputs and history; a synthetic storage harness is supporting evidence only.
  8. WALL-AT-08 · System migration and modalities. Update a library system without modifying the pinned project. Preview and evaluate migration on a branch. Prove equivalent operations from numeric editing, pointer input and a reviewed language proposal, with usable direct editing when AI is unavailable.

Semantic-version rules

Compatibility claims are normative and machine-testable.

Major

Any change requiring a consumer, stored world or dependent capability to change before it can continue safely.

  • Requires an explicit migration or parallel reader.
  • Cannot silently replace the prior major.
  • Must declare affected capabilities and worlds.

Minor

Additive, backward-compatible capability or contract expansion.

  • Existing valid inputs remain valid.
  • Existing semantics do not change.
  • New behavior is opt-in or safely defaulted.

Patch

Backward-compatible correction that does not alter a public contract or intended result.

  • Regression evidence is mandatory.
  • A numerical-result change must be disclosed.
  • No hidden schema or permission expansion.

Pre-1.0

A minor change may be incompatible, but Plasma never treats that instability as permission for silent breakage.

  • Each 0.MINOR is a compatibility boundary.
  • Migration and affected-world analysis are still required.
  • Patches remain backward-compatible.

Plasma release bundle

The only promotable unit is an immutable bundle, not a loose collection of latest components.

schema: plasma-release-bundle/1.0.0 release_id: plasma-release:sha256:<canonical-manifest-digest> release_label: 2026.08.31.1 status: candidate previous_release_id: <immutable-bundle-id> runtime: { version, commit, digest, sbom_digest } schemas: { world_state, foundry_manifest, observed_state, event } capabilities: [{ id, version, commit, digest, compatibility }] agents: [{ id, version, model, tools, prompt_digest, permission_profile }] evaluators: [{ id, version, fixture_set, digest, independence_class }] project_validation: { branch, world_revision, coherent_cut, affected_scope } evidence_set: { id, digest, claims } migrations: [{ id, from, to, reversible, evidence_ref }] approval: { authority, decision_id, timestamp, signature_ref }

Migration, rollback and recovery

Rollback restores a proven configuration; it never erases the failed history.

Migration contract

  • Declare from/to versions and compatible reader ranges.
  • Make migrations deterministic, idempotent and fixture-tested.
  • Prefer expand → migrate → verify → contract.
  • Preserve the pre-migration world and provide a rehearsal branch.
  • Irreversible migrations require explicit authority and a recovery artifact.

Rollback contract

  • Move the active release pointer to the last proven compatible bundle.
  • Create a new rollback event; never rewrite prior events.
  • Restore capability and schema compatibility as one transaction.
  • Revalidate affected coherent worlds before declaring recovery.
  • Retain the rejected bundle, evidence and failure diagnosis.

Recovery contract

  • Back up canonical manifests, event logs, schemas, evidence and artifact storage.
  • Define recovery point and recovery time objectives before production use.
  • Verify restore procedures with scheduled recovery drills.
  • Keep the lifeboat kernel independently deployable and minimally changeable.
  • Require break-glass actions to be time-limited and fully audited.

Evidence integrity

  • Machine evidence is append-only and content-addressed.
  • Corrections supersede prior evidence; they do not delete it.
  • Record evaluator, fixtures, environment, inputs and output digests.
  • Candidate code cannot alter its governing evidence after evaluation starts.
  • Retention and legal/privacy deletion are separate governed workflows.

Minimum engineering controls

Required before a bundle may become active.

1Canonical source: versioned specs and schemas live with code; generated HTML and manifests declare their source revision.
2Protected integration: reviewed change, bounded permissions, passing CI and no direct mutation of active releases.
3Reproducible build: locked dependencies, recorded toolchain, artifact digest, SBOM and isolated build environment.
4Contract verification: schema, compatibility, migration, regression, security and affected-world tests produce immutable evidence.
5Operational readiness: observability, resource budgets, failure limits, rollback target and recovery procedure are declared.
6Independent approval: evaluator independence is proven and a named human authority promotes the exact release-bundle digest.
